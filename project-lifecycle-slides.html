How We Deliver Projects
Without the Chaos

A shared playbook for Sales, Project Management, Software, and Controls — so everyone knows what's expected, when it's expected, and who owns it.

Why this exists

The real problem

Software and Controls are the last to know — and the first to be blamed when we're late.

🤝

The deal closes

Sales promises features, timelines, and capabilities. Software hears about it later — sometimes much later.

📄

Documents land last-minute

FSD and HI docs are due and nobody asked Software what was even feasible before signing.

🔥

We scramble

No staff planned. No schedule built. We absorb the project and somehow make it work — at our cost.

The solution

The fix is simple: gates

A gate is a checkpoint. Work cannot move forward until the gate is cleared. No exceptions. No workarounds.

✅

Before the contract

Software and Controls review every deal. They sign off on feasibility before anyone promises anything.

👤

At kickoff

One PM. One TPM. Named. Accountable. No more "we have three PMs" meaning no one is responsible.

📋

Before building

Requirements are written, signed, and approved before a single line of code is written.

The lifecycle

Every project has 10 stages

1. Qualify 2. Shape Solution 3. Sign Contract 4. Intake / Kickoff 5. Requirements 6. Design & Plan 7. Build & Integrate 8. Site Readiness 9. Go-Live 10. Closeout

No stage gets skipped. Each one has a clear exit gate — a checklist that must be complete before the next stage starts.

Stages 1 – 2

Before the contract is signed

🔍
Sales qualifies the opportunity and assigns it an archetype (Greenfield / Recontrol / Upgrade)This determines how much lead time Software and Controls need
⚡
Software Lead gives a rough effort estimate within 48 hoursNo estimate = no sales resource allocation. This is not optional.
⚡
Controls Lead gives a rough effort estimate within 48 hoursSame rule applies.
🤝
Solution Architect shapes the solution with the customer — Software and Controls are named participantsNot an afterthought. Part of the room.
✍️
Software Lead and Controls Lead sign the Technical Feasibility documentIf it's not signed, the SOW doesn't get drafted.
When things don't line up

What happens when Sales over-promised?

↩ Reconciliation Loop A — Feasibility Impasse

If Sales has promised capabilities that aren't feasible with our product, we stop. SA, Software, and Controls define what is feasible. Sales goes back to the customer to realign scope before we write a single requirement.

This loop exists so we never find out something isn't buildable after a contract is signed.

Stage 3

Signing the contract

The SOW (Statement of Work) is the rulebook for the project. If it's wrong, everything downstream is wrong.

🚦 Gate — SOW Internal Sign-off

Before anyone signs a contract with the customer, these must be true:

  • Software Lead has reviewed and signed off on scope language
  • Controls Lead has reviewed and signed off on scope language
  • Assumptions and exclusions are written explicitly in the SOW
  • A change order process is defined in the SOW
Stage 4 — T₀

Project Kickoff

Within 5 business days of signing, we hold a kickoff meeting with the full team.

🛑
One PM named as owner — full name, no committeeIf there are 3 PMs with the same title, nobody is accountable.
🛑
One TPM named as software scope owner — full nameThis person owns the FSD, the HI docs, and the software schedule.
📁
Signed SOW goes to every team memberNo one builds from memory or verbal briefings.
🗓
Software and Controls capacity formally reserved in the scheduleBy name, not "a developer." Unnamed capacity is not capacity.

Stage 5

Writing the requirements

The FSD (Functional Spec) and HI (Host Interface) documents are the blueprint. Everyone builds from them.

✍️
TPM leads — SA validates — Software and Controls co-author their sectionsTPM can't write software requirements alone. They need the people who build it in the room.
🔗
Every requirement traces back to a scope item in the SOWIf it's not in the SOW, it doesn't belong here without a Change Request.
🛑
No build starts until FSD + HI are signed and customer-approved
↩ Reconciliation Loop C — Requirements Gap
If discovery surfaces scope not in the SOW → Change Request immediately. Not absorbed. Not done as a favour.
Stages 6 – 7

Planning & Building

📐

Design & Plan first

Named staff, sprint plan, integration test strategy. Hardware delivery dates mapped to software milestones. Approved before build starts.

🔨

Build iteratively

Regular software-controls-hardware integration checkpoints. Issues found early are cheap. Issues found on-site are expensive.

🚫

New requests = CR

Any new screen, feature, or integration added during build goes through a formal Change Request. Work doesn't start without approval.

↩ Reconciliation Loop D — Integration Conflict
If software and controls interface behaviors conflict → joint resolution session within 48h. TPM arbitrates. PM assesses schedule impact.
Stage 8

Site Readiness — the travel gate

Nobody travels to a customer site until this gate is cleared.

🚦 Gate — FAT/SAT Checklist
  • Software Lead signs site readiness checklist
  • Controls Lead signs site readiness checklist
  • All acceptance criteria tested and documented
  • No P1 (critical) defects outstanding
  • Rollback / contingency plan exists

Showing up to site to "figure it out" is not commissioning. It is expensive, embarrassing failure.

Stage 9

Go-Live & Hypercare

✅
Customer signs off on go-live criteria before cutoverWe don't flip the switch and hope. Criteria are agreed in advance.
📟
Software and Controls are on a named hypercare rotaSomeone is on call. The customer knows who to call. It's written down.
🏷
Post-launch issues are tagged: warranty vs. billable changeNot everything reported after go-live is our bug to fix for free.

Project Closeout

Non-negotiables

8 rules that are not optional

We'll cover each one. These are the lines we don't cross — because crossing them is what created the chaos we're fixing.

Rules cover: pre-SOW sign-off · named PM/TPM · software capacity · post-SOW change requests · FSD baseline · site readiness · verbal commitments

Use the ▶ button to step through each rule one at a time →

Non-negotiable · Rule 1 of 8
Rule 1

No Technical Feasibility Gate = No SOW

Software and Controls must sign the Technical Feasibility document before any Statement of Work is drafted. Sales does not own feasibility — engineering does. If engineering hasn't signed, the SOW doesn't exist.

Non-negotiable · Rule 2 of 8
Rule 2

No Named PM/TPM Pair = No Project Start

Every project has exactly one PM (delivery owner) and one TPM (software scope owner). Three people with "Project Manager" in their title means zero people are accountable. If there's no named pair, the project does not start scheduling.

Non-negotiable · Rule 3 of 8
Rule 3

No Software/Controls SOW Sign-off = No Contract

Any scope item touching software UI, integrations, reporting, or PLC logic requires written sign-off from the relevant lead before contract execution. If it impacts them, they approve it. Period.

Non-negotiable · Rule 4 of 8
Rule 4

Post-SOW Scope = Formal Change Request

Any customization, new screen, new feature, or integration added after the SOW is signed requires a Change Request with estimated hours, schedule impact, and commercial impact — before a single hour of work begins. No exceptions. No favors.

Non-negotiable · Rule 5 of 8
Rule 5

No FSD/HI Baseline = No Build

The build does not start until the Functional Spec and Host Interface documents are baselined, customer-approved, and signed by TPM, Software Lead, and Controls Lead. Verbal requirements are not scope. They are misunderstandings waiting to happen.

Non-negotiable · Rule 6 of 8
Rule 6

No Site Readiness Sign-off = No Travel

No engineer travels to a customer site until the FAT/SAT checklist is complete and signed by Software and Controls. Arriving on-site to "figure it out" is not commissioning — it is expensive, embarrassing failure billed to us.

Non-negotiable · Rule 7 of 8
Rule 7

Software Capacity Is Not On-Demand

Software engineers are not a utility you turn on when the project arrives. Capacity must be reserved by name in the scheduling system at project intake — weeks or months before work starts. Surprise projects don't absorb spare capacity. They create debt, burnout, and missed deadlines.

Non-negotiable · Rule 8 of 8
Rule 8

Verbal Commitments Are Scope Debt

Anything promised to a customer by Sales, KAM, or SA that is not in the SOW is uncontracted scope. It must be surfaced immediately, logged, and resolved via a Change Request or SOW amendment. "I told them we could do that" is not a work order.
