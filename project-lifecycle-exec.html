Engineering Leadership — Working Session

Software Delivery Is a Business Risk

An assessment of our current project intake model, its operational impact, and a proposed governance framework to correct it.

Presented by: Principal Software Engineer  | 

Purpose

Why We Are Here

  • Software and Controls teams consistently receive project scope after key commitments are already made — sometimes the week documents are due.
  • We are not resourced for work we don't know is coming. Staffing, scheduling, and architecture decisions require lead time.
  • The current model relies on informal communication — hallway conversations, last-minute emails, and institutional gossip.
  • This session proposes a formal governance model with clear gates, role accountability, and mandatory software engagement points.
Objective

Leave this session with leadership alignment on a process that treats software readiness as a delivery prerequisite — not an afterthought.

Current State

How Projects Actually Flow Today

1.

Sales closes the deal

Scope and commitments made without software or controls input. Feasibility is assumed, not confirmed.

2.

SOW is written

Key functions are already agreed upon. Software is occasionally consulted informally — if at all.

3.

Project kicks off

Software and Controls find out about scope. FSD and HI docs are due. The scramble begins.

4.

We make it work

Teams absorb undocumented scope, unplanned customizations, and resource gaps. Delivery suffers.

Result

Reactive delivery, compressed timelines, unplanned scope, and developer burnout — on every project.

Root Cause

This Is a Structural Problem, Not a People Problem

  • No defined engagement gates. Software and Controls have no formal point at which they are required to participate. Involvement is discretionary.
  • Accountability is diffuse. We have PMs, TPMs, KAMs, and SAs — and no single person owns the technical commitment before a contract is signed.
  • The SOW is written without a technical baseline. Scope is committed commercially before it is validated technically.
  • No intake process. Projects enter our system without a standardized assessment of type, complexity, or resource requirement.
  • Customizations are untracked. Feature additions, new screens, and configuration changes are absorbed informally with no change control.
Impact

Where This Hurts the Business

Delivery Risk

  • Compressed design and build windows
  • Integration conflicts discovered late
  • Site readiness failures caused by upstream gaps
  • Go-live delays attributed to software

Resource Risk

  • Cannot staff what we don't know is coming
  • Engineers pulled from active work to cover unplanned scope
  • No pipeline visibility for hiring or contractor planning
  • Burnout from perpetual reactive mode

Financial Risk

  • Untracked customizations delivered for free
  • Scope creep absorbed silently — not billed
  • Cost overruns not attributed to their source
  • No mechanism to escalate out-of-scope work

Organizational Risk

  • No institutional documentation — oral tradition only
  • Key knowledge siloed in individuals, not process
  • Onboarding new team members into chaos
  • Sales over-promises with no correction mechanism
Proposal

A Governed Lifecycle with Mandatory Engagement Points

The fix is not more meetings. It is a defined process with gates that cannot be bypassed — and clear ownership at each stage.

What Changes

  • Software engaged at Opportunity Qualification — not at kickoff
  • No SOW issued without Software + Controls sign-off
  • Formal intake for every new project
  • All customizations processed through Change Request
  • One accountable owner per stage

What Doesn't Change

  • Sales still owns the customer relationship
  • PM still owns the delivery schedule
  • SA still does on-site configuration work
  • Software and Controls still build and deliver
  • We are adding structure — not replacing people
Framework

Three Project Archetypes — Each Requires Different Lead Time

GF

Greenfield

New system, new site. Highest complexity. Full lifecycle applies. No assumptions about reuse.

⟶ Software engaged: Opportunity stage
Pre-SOW lead time: 4–8 weeks
RC

Recontrol / Major Upgrade

Existing system, major scope change. Legacy constraints apply. Architecture review required.

⟶ Software engaged: Opportunity stage
Pre-SOW lead time: 3–6 weeks
MU

Minor Upgrade / Add-On

Targeted change to existing system. Lower risk but still requires formal intake and CR tracking.

⟶ Software engaged: At intake
Pre-SOW lead time: 1–2 weeks
Note on Customizations

Any project can have customizations added at any time. All customizations — new screens, features, integrations, UI changes — require a formal Change Request before work begins. No CR = no work.

Governance

Three Gates That Cannot Be Bypassed

  • Gate 1 — SOW Freeze: No contract is issued without written sign-off from Software Lead and Controls Lead on scope, effort estimate, and feasibility. A sales commitment without technical validation is a liability, not a win.
  • Gate 2 — Design Freeze: No build begins without a baselined FSD and approved architecture. Scope that is not documented does not get built. Changes after this point require a formal Change Request.
  • Gate 3 — Site Readiness: No travel is approved, no commissioning begins, without Software and Controls sign-off that systems are ready. Site failures caused by software unreadiness are preventable and unacceptable.
If a Gate Is Skipped

The bypass is a documented exception — approved by leadership, with risk ownership assigned. Skipping a gate does not mean the risk disappears. It means someone owns the risk explicitly.

Governance

When Scope Changes Mid-Stream — Controlled Loops

Projects rarely go in a straight line. The process accounts for this with defined reconciliation points — not ad-hoc rework.

A

Feasibility Impasse

Technical assessment contradicts proposed scope. Returns to Solution Shaping before SOW is issued.

B

Scope Inflation

SOW draft reveals scope beyond original estimate. Returns for commercial re-alignment before contract.

C

Requirements Gap

Discovery reveals missing or conflicting requirements. Returns to customer for clarification before design freeze.

D

Integration Conflict

Build reveals hardware/software integration issue. Requires joint resolution — not silent workarounds.

Governance

Customizations Are Not Free — The Change Request Process

Every project can receive customizations. Every customization must go through a CR before work begins. No exceptions.

What Triggers a CR

  • New UI screen or component
  • New feature not in baselined FSD
  • Integration change post-design freeze
  • Configuration change with downstream impact
  • Any customer-requested modification post-SOW

CR Requires

  • Written description of the change
  • SW Lead effort estimate
  • Impact assessment on timeline
  • Customer sign-off or internal approval
  • Commercial impact evaluated (billable or absorbed — documented either way)
The Problem Today

Customizations are absorbed informally, delivered for free, and attributed to software "being slow." This ends. Undocumented work is not work we agreed to do.

Gate Checklist

Gate 1: SOW Freeze — What Must Be True Before This Gate Passes

✔ Software Lead has reviewed proposed scope and signed off on feasibility
✔ Controls Lead has reviewed hardware/software integration surface and signed off
✔ Project type classification confirmed (Greenfield / Recontrol / Minor Upgrade)
✔ High-level effort estimate provided by SW Lead and Controls Lead
✔ Known constraints, risks, and dependencies documented
✘ Gate fails if Software or Controls have not been consulted on scope
✘ Gate fails if effort estimate is missing or based solely on sales assumptions
✘ Gate fails if integration dependencies are unresolved

Non-Negotiables

Eight Rules. Not Guidelines.

  • Software engagement is a gate, not a courtesy. No feasibility review = no SOW.
  • No contract without technical sign-off. SW + Controls sign the SOW or the contract does not execute.
  • No build without a baselined FSD. Undocumented scope is not agreed scope.
  • No travel without site readiness sign-off. SW + Controls confirm readiness before commissioning begins.
  • All customizations require a Change Request. No CR = no work. Verbal agreements are not work orders.
  • One accountable DRI per stage. When accountability is shared, it is owned by no one.
  • Retrospectives are mandatory. Every project closes with a documented retrospective. Lessons feed back into process.
  • Escalation paths are documented. Disagreements on scope, timeline, or resources have a defined resolution path — not a shouting match.

Leadership Requirements

This Cannot Work Without Leadership Backing

  • Sales must be told that scope commitments require SW/Controls review first. This is a commercial and legal conversation — not just an engineering request. Leadership must deliver this message.
  • TPM accountability must be enforced. TPMs are the technical scope owners. If they are not producing FSD/HI documents and managing SW engagement, that is a performance issue, not a process gap.
  • PM proliferation must be addressed. Having 3–4 PMs on a project with the same title and diffuse responsibilities produces no accountability. One PM per project owns delivery. Others are support.
  • Process gates must be backed by policy, not good intentions. If gates can be bypassed without consequence, they will be bypassed. Leadership defines and enforces the consequence.
Next Steps

Implementation — Phased Approach

  1. 1
    Immediate (0–30 days): Adopt the intake checklist for all new projects entering the pipeline. Assign DRI roles for all active projects. No new project enters without a type classification and a named TPM.
  2. 2
    Short-term (30–60 days): Implement Gate 1 (SOW Freeze) for all new deals. Sales is briefed. TPM is responsible for organizing SW + Controls review before SOW is issued.
  3. 3
    Medium-term (60–90 days): Full 10-stage lifecycle with all 3 gates operational. Change Request process in place for all customizations.
  4. 4
    Ongoing: Monthly metrics review. Quarterly retrospective on process health. Governance document versioned and owned.
Formal Asks

What I Am Asking Leadership to Approve Today

1
Mandate that Software and Controls are consulted before any SOW is issued

This is a policy change, not an engineering request. It requires a directive from leadership to Sales and Commercial.

2
Ratify the 10-stage lifecycle and 3 gates as the operating standard for project delivery

Engineering will own the technical governance document. Leadership ratifies it as company process — not department preference.

3
Define escalation and exception policy

When gates are bypassed, who approves it and who owns the risk. This cannot be an informal decision.

4
Monthly engineering/leadership delivery review cadence

Metrics reviewed, exceptions discussed, process adjusted. 30 minutes monthly. Keeps the process honest.

Risk Analysis

What Happens If We Don't Change the Model

  • Continued late delivery. Projects will keep running long because scope is never locked before build begins. This is not a staffing problem — it is a process problem. More engineers will not fix it.
  • Invisible financial loss. Customizations will continue to be delivered for free with no commercial tracking. The revenue impact is real but unquantified.
  • Talent risk. High-performing engineers do not stay in organizations that perpetually operate in reactive mode. This is a retention issue with a long tail.
  • Scalability ceiling. We cannot grow project volume on an oral tradition. Every new hire inherits the chaos. Process is a precondition for scale.
Bottom Line

The current state is not sustainable as a business model for project delivery. Governance is not overhead — it is how we protect margin, protect our people, and protect our customers.
